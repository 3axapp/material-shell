# Тесты

Проверки двух видов. Окно настроек — обычный GTK-модуль, поэтому его тесты
загружают `prefs.js` в отдельный процесс `gjs`. Само расширение работает только
внутри gnome-shell, поэтому тесты в `tests/shell/` запускают собственный
вложенный шелл и выполняются внутри него.

## Запуск

```sh
make test        # окно настроек, или: gjs -m tests/prefs-check.js
make test-shell  # внутри вложенного шелла, или: tests/shell/run.sh
```

Обе цели сначала выполняют `make compile`: тесты читают `dist/`, а не `src/`.

| Файл | Что это |
|------|---------|
| `tests/prefs-check.js` | Проверяет, что окно настроек помещается и каждая строка читает и пишет свой ключ. При ошибке выходит с ненулевым кодом. |
| `tests/prefs-measure.js` | Печатает деревом ширину, которую запрашивает каждый виджет окна. Диагностика, а не тест. |
| `tests/harness.js` | Загружает `dist/prefs.js` в `Adw.PreferencesWindow`. |
| `tests/stub/` | Заглушка ресурса шелла, который импортирует `prefs.js`. |
| `tests/shell/run.sh` | Запускает каждый `tests/shell/*.test.js` в собственном вложенном шелле. При ошибке выходит с ненулевым кодом. |
| `tests/shell/lib.js` | Помощники для тестов в шелле: `until`, `check`, `run`, `watchMenus`. |
| `tests/shell/*.test.js` | Сами тесты в шелле. |

## Тесты окна настроек

- **Нужен дисплей**: виджеты должны быть отрисованы, чтобы сообщить свои
  размеры. Годятся и Wayland, и X11.
- **Ваши настройки не трогаются.** `harness.js` до создания любого
  `Gio.Settings` ставит `GSETTINGS_BACKEND=memory` и проверяет, что он
  подействовал.
- **`prefs-measure.js` — первое, что запускать, когда окно выглядит
  обрезанным**: он называет виджет, который раздувает ширину. Так нашёлся
  [#8](https://github.com/3axapp/material-shell/issues/8): скрытая страница
  Hotkeys поднимала минимальную ширину содержимого до 765 px, окно открывалось
  шириной 640 px, а libadwaita в таком случае обрезает содержимое, а не
  растягивает окно.
- **Заглушка.** `prefs.js` импортирует `ExtensionPreferences` из
  `resource:///org/gnome/Shell/Extensions/js/extensions/prefs.js`. Этот ресурс
  зарегистрирован только внутри приложения «Расширения», а настоящий модуль
  тянет за собой D-Bus-сервис расширений. `tests/stub/prefs.js` даёт те же
  экспорты и на каждом запуске компилируется в gresource по тому же пути,
  поэтому нужен `glib-compile-resources`.

## Тесты внутри шелла

### Как устроены

Для каждого `tests/shell/*.test.js` скрипт `run.sh`:

1. создаёт временный `HOME` (`mktemp -d`), где нет ничего из ваших настроек;
2. копирует туда `dist/` как расширение;
3. переименовывает `extension.js` в `extension.real.js` и кладёт на его место
   обёртку из двух строк:
   ```js
   export { default } from './extension.real.js';
   import './shell-test/<имя>.test.js';
   ```
4. запускает `gnome-shell --devkit` под `dbus-run-session` с расширением,
   включённым с самого старта, и общим таймаутом 60 секунд.

Тест работает в том же процессе, что и расширение, и видит всё: `global.ms`,
менеджеры, акторов. Сборка при этом не трогается.

Нужны пакет `mutter-devkit` и работающая сессия: на каждый тест на несколько
секунд открывается окно Mutter Development Kit.

Под `--devkit` шелл стартует без мониторов, а Mdk добавляет свой примерно через
секунду. Обычно расширение успевает загрузиться раньше, но не всегда, поэтому
полагаться на этот порядок нельзя. Тесту, которому монитор нужен с самого
старта, подошёл бы `--headless --virtual-monitor 1280x800`: он проверен и окон
не открывает, но `run.sh` пока так запускать не умеет.

**Старт без монитора** ([#12](https://github.com/3axapp/material-shell/issues/12))
проверяется в режиме `--headless` без монитора. Этот режим включает строка
` * shell-test: headless` в шапке файла теста. Монитор тест добавляет сам:
у Mutter вызываются ScreenCast `CreateSession` → `RecordVirtual` → `Start`.
Виртуальный монитор появляется, только когда к потоку PipeWire подключается
потребитель. Потребителем служит `gst-launch-1.0 pipewiresrc ! fakesink`, и на
нём легко споткнуться:

- `pipewiresrc` ищет узел по `object.serial`, а Mutter в `PipeWireStreamAdded`
  сообщает id. Serial берётся из `pw-dump <id>`, причём в выводе бывают и
  объекты, у которых serial совпадает с этим id.
- Без `media.type=Video` в `stream-properties` WirePlumber не связывает
  потребителя с видеопотоком и отвечает `target not found`.

Нужны запущенные PipeWire и WirePlumber и плагин `gst-plugin-pipewire`. Пример —
`no-monitor-at-start.test.js`
([#20](https://github.com/3axapp/material-shell/issues/20)).

### Как читается результат

`lib.js` пишет результаты в лог под своим доменом:

```
MSTEST-Message: …: PASS <имя>
MSTEST-Message: …: FAIL <имя>: <подробности>
MSTEST-Message: …: DONE failed=<число>
```

`run.sh` считает прогон проваленным, если:

- есть хоть одна строка `FAIL`;
- нет итоговой `DONE` — шелл завис или упал;
- в логе есть `JS ERROR`, стек которого проходит через файлы расширения.

Предупреждения `Gjs-CRITICAL` про уже уничтоженный `TaskActiveIndicator`,
которые расширение печатает при выключении шелла, не засчитываются. Это
отдельная, пока не разобранная история.

Если тест провален, временный `HOME` и лог остаются, а путь к логу
печатается. `KEEP=1 tests/shell/run.sh` оставляет их и для прошедших тестов.

### Как написать тест

Создайте `tests/shell/<имя>.test.js`:

```js
import { check, run, until } from './lib.js';

run(async () => {
    const loaded = await until(() => global.ms.loaded, 15000);
    check('extension loaded', loaded);
});
```

- **Ждите устоявшегося состояния** через `until()`, а не смотрите один раз:
  шелл приходит в себя за несколько кадров. Например, рамка окна до первого
  кадра равна `0×0` и доходит до размера плитки только через несколько сотен
  миллисекунд — разовый замер тут даёт ложное падение.
- **`run()` завершает шелл**, когда тело теста закончилось. Исключение в теле
  засчитывается как `FAIL`.
- **Для бага сначала красная фаза**: запустите тест на старом коде и убедитесь,
  что он падает, и падает по той причине, которую вы ловите. Потом
  исправление.
- **Файл теста не проходит через сборку** — он копируется как есть. Поэтому в
  нём можно `?.` и object spread, в отличие от `src/`.
- **Окно из теста** открывает `Gio.Subprocess` с `gjs -c` и окном GTK4: шелл
  передаёт процессу свой `WAYLAND_DISPLAY`, окно попадает в плитку. Пример —
  `no-menu-flash-on-new-workspace.test.js`. Не убивайте клиента сразу после
  появления окна: `force_exit()` примерно через секунду дал `JS ERROR` из
  `MsWindow.metaWindowUnManaged`. Обычное закрытие (`meta_window.delete()`)
  через 3 с ошибки не даёт, а с остановкой шелла клиент выходит сам.
- **Не ждите кадров.** Вложенный шелл рисует их редко, `after-paint` за весь
  прогон приходит считанные разы. То, что должно попасть на экран, проверяйте
  по состоянию актора (`mapped`) в ближайшем `GLib.idle_add`. Так устроен
  `watchMenus()`: меню, которое осталось mapped закрытым, будет в следующем
  кадре.

Что ещё проверено в спайке, но в тесты пока не вынесено:

- **Хоткеи.** Виртуальная клавиатура
  `Clutter.get_default_backend().get_default_seat().create_virtual_device(Clutter.InputDeviceType.KEYBOARD_DEVICE)`
  и её `notify_keyval()` нажимают сочетания: `Super+S` переключил стол.

### Чего эти тесты не заменят

Клавиатура во вложенный шелл приходит через окно Mdk или через виртуальное
устройство, а не с настоящего железа. Поэтому залипание клавиш и фокус
Wayland-клиентов ([#2](https://github.com/3axapp/material-shell/issues/2),
[#10](https://github.com/3axapp/material-shell/issues/10)) финально
проверяются в настоящей сессии, как и работа с реальными мониторами.
